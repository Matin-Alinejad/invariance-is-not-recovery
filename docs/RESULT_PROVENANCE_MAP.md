# Result provenance map

This document traces every released computational result from its registered configuration through the production/analysis code to the processed evidence and reference artifacts. It is intentionally separate from the root README so the repository landing page can remain focused on code, data, and reproduction instructions.

## Sample-size schedule provenance

The integer sample-size schedule is owned by the production function `calibrated_sample_size(...)` in `code/experiments/run_recovery_experiments.py`. `analysis/generate_reference_artifacts.py` imports that same function and reads the reference constants from `configs/primary_scaling.yaml`; it does not duplicate the rounding rule.

The registered schedule is:

| `p` | `gamma = 1.0` | `gamma = 1.25` |
| ---: | ---: | ---: |
| 20 | 1000 | 796 |
| 50 | 2500 | 2500 |
| 75 | 3750 | 4151 |
| 100 | 5000 | 5947 |
| 150 | 7500 | 9871 |

The regression suite and reported-result validator both check these exact values.

## Reported numerical validation

`analysis/verify_reported_results.py` recomputes the released numerical assertions from the 25-file evidence bundle and additionally checks the exact integer sample-size schedule through the production `calibrated_sample_size(...)` function. The schedule checks were added specifically to prevent a duplicated rounding convention from drifting away from executed sample sizes.

## From-scratch closure

The full reconstruction path is:

1. execute the registered shards with `scripts/run_vm_shard.sh` on the four reference Ubuntu VMs;
2. merge/analyze the primary, sensitivity, and matched-local blocks with `scripts/merge_and_analyze_campaign.sh`;
3. execute and merge the non-overlapping precision extension with `scripts/run_precision_extension_shard.sh` and `scripts/merge_precision_extension.sh`;
4. run `scripts/reconstruct_release_results.sh` to recompute structural diagnostics, rebuild the 25-file evidence bundle, compare it with the released evidence, rerun numerical validation, and regenerate/verify the reference artifacts.

The reference campaign used four Ubuntu VMs, each with **32 vCPUs, 64 GB RAM, and 200 GB local disk**, with eight Python workers per VM.

## Mathematical source

`formal/` contains pinned Lean 4 / Mathlib source corroborating selected finite-combinatorial, Gaussian-null, recovery-composition, Student-t, and information-theoretic components. `formal/build_all.sh` is the public build entry point when Lean/Lake is installed.
